Branch: feat/audit-record-narrative (based on latest main).
Depends on brain-core's feat/audit-proposal-decided-snapshot landing first
(adds outputs.proposal_summary to proposal.decided audit events) - but
degrades safely if this ships first, since every new read is optional-
chained with a fallback to today's behavior.

Problem: the Audit Record popup for a proposal.decided event renders
"Proposal decided - acknowledge (prop_xxx)" and nothing else - no reasoning,
no severity, no link to what was actually decided. Separately, `linked` is
hardcoded to [] on every mapped record even though AuditRecordPopup.tsx
already has full working render/navigate code for linked-evidence chips
(rule/vendor/invoice/proposal) - it's just never fed data.

Changes, all in client/src/lib/brainAudit.ts:

1. Add proposalSummaryFrom(e: BrainAuditEvent) reading
   e.outputs?.["proposal_summary"] (typed loosely, all fields optional -
   absent on events predating this, and on money-path decisions which don't
   emit this key at all).

2. classifyProposalDecided(): prefer proposalSummaryFrom(e)?.narrative as
   the record's summary when present and non-empty; fall back to the
   existing "Proposal decided - <decision> (<id>)" line otherwise. Never
   assume the new field exists.

3. mapAuditEventToRecord(): 
   - surface recommended_remediation as the lifecycle step's `note` (same
     pattern already used for the full wiki.question text) when it differs
     from the summary
   - populate `linked` with a { kind: "proposal", label: proposalId,
     refId: proposalId } entry whenever action === "proposal.decided" and
     inputs.proposal_id is a string - regardless of whether proposal_summary
     is present, since even the bare id is worth linking

   This is safe to ship even before openProposalDetail/resolveProposal
   learns to resolve live GET /v1/proposals/{id} data (it currently only
   resolves the demo mock corpus in client/src/lib/openProposalDetail.ts) -
   confirmed AuditRecordPopup.tsx already falls back to a plain,
   non-tappable "(proposal unavailable)" chip when resolveProposal misses,
   same honesty pattern used everywhere else in this file. Making the chip
   actually tappable for live tenants is a separate, larger follow-up (needs
   resolveProposal to also check useBrainProposals data, not just
   MOCK_PROPOSALS) - not in scope here, please file it separately rather
   than trying to fold it in.

4. Separately, in client/src/components/AnchorStatus.tsx: replace the
   pending-state copy "Proof incomplete. Anchoring usually completes within
   a few hours." with "Proof incomplete. This record hasn't been anchored
   on-chain yet." - the component has no real queue-depth/age data to back
   the time estimate, and it's actively false right now given the ongoing
   anchor-wallet backlog. (Making this reflect real backlog state is a
   bigger fix needing the anchor worker's health data plumbed through -
   also not in scope here.)
