CONTEXT
This is Brain Finance's inbox review UI. Proposal cards (Invoice Agent, Collections
Agent, Cash Agent, Close Agent) currently render raw internal object IDs directly
in the card body (e.g. "counterparty: cp_01KYSF0QP1AR1SR7BN2430HV67",
"invoice: inv_01KYSF0QRB8Y8GD2SCV8M5PW7V"). This is not usable for a human making
an approve/reject decision.

TASK 1 — Human-readable proposal cards (all four agent types)

1. Find the shared proposal/review modal component(s) used across Invoice Agent,
   Collections Agent, Cash Agent, and Close Agent (likely one shared component
   rendering different proposal payloads).
2. Wherever a field currently displays a raw entity ID (counterparty_id,
   invoice_id, vendor_id, account_id, etc.), resolve it to its human-readable
   name before rendering — customer/vendor name, invoice number, account name,
   etc. Use whatever lookup/join is already available server-side; if the
   proposal payload doesn't currently include the resolved name, add it to the
   payload shape rather than resolving client-side.
3. Move raw technical IDs out of the primary card view into a collapsed
   "Technical reference" section (collapsed by default) — keep them accessible
   for audit/debugging, just not front-and-center.
4. Add supporting context fields that help the approval decision, scoped to
   what's already available in the data model per agent type, e.g.:
   - Collections: due date, prior reminder count this period, recipient email,
     a preview of the outbound message before approving
   - Invoice: vendor name, PO reference if present, prior payment history flag
   - Cash / Close: whatever equivalent human-readable context already exists
     in the underlying records
   Don't invent data that isn't available — only surface what the backend
   already has.
5. Keep the layout compact: name/avatar block at top, 2-4 supporting detail
   rows, collapsible message preview, collapsible technical IDs, then the
   Reject/Approve actions. Follow the existing dark theme and button styling
   already used in the Needs Review modal.
6. Apply this consistently across all four agent proposal types — same
   component pattern, not a one-off fix just for Collections.

TASK 2 — Fix amount/number formatting regression across the platform

We previously had proper number formatting for currency amounts (thousands
separators, fixed decimals) and it's no longer working correctly — e.g. amounts
rendering as "42000.00" instead of "$42,000.00". This shows up at least in the
proposal cards and in Brain assistant chat responses.

1. Search the codebase for the currency/number formatting utility that was
   originally used (likely something using Intl.NumberFormat or a custom
   formatCurrency/formatAmount helper). Identify why it's not being applied
   consistently — check for:
   - Places where raw numeric values are interpolated directly into strings
     or JSX instead of passing through the formatter
   - The assistant response pipeline specifically — check if amounts coming
     back from tool calls / agent outputs are formatted before being inserted
     into the chat response text, or if they're passed through as raw numbers/
     strings from the backend
   - Any recent refactor, prompt template change, or new proposal/response
     rendering path that bypassed the existing formatter
2. Fix the root cause, not just individual instances — if there's a shared
   formatting utility, make sure every surface (proposal cards, inbox list
   items, Brain assistant chat responses, insights, audit log) actually calls
   it. If the assistant's chat responses are generated via an LLM prompt that
   includes raw numbers, make sure the formatting instruction is still present
   in that prompt/template, or better, format the numbers before they're
   interpolated into the response rather than relying on the LLM to format them.
3. Apply consistently: currency as $X,XXX.XX (2 decimals), percentages with
   sensible precision, no raw floats leaking through anywhere in the UI or in
   assistant-generated text.
