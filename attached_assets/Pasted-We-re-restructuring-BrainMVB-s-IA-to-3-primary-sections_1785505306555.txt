We're restructuring BrainMVB's IA to 3 primary sections — Overview, Decisions,
Ledger — plus reorganized Settings, following the attached prototype
(brain-ux-vision-v6.html). Reference it for exact page structure, interaction
behavior, and copy — but NOT for visual styling. Use our existing design system
(colors, spacing, typography, component patterns already in BrainMVB) throughout;
the prototype's dark/purple theme is a placeholder standing in for our real one.
Anywhere the prototype needs a component we don't have yet (e.g. a priority-tier
row style, a confidence bar), build it to match our existing visual language, not
the prototype's.

DO NOT TOUCH — these are working and out of scope:
- Sign up / sign in / auth flows
- "Continue with Demo" and the fresh-per-visitor demo tenant creation logic
- The Brain Assistant chat panel (right rail) — keep it present and wired exactly
  as it is today on every page in the new structure. It was omitted from the
  prototype only to keep the mockup focused, not because it should go away.
- Any brain-core API calls already wired and working — reuse them as-is

GOAL: reuse existing logic and existing brain-core endpoints wherever the data
already exists. This is an IA and interaction reorganization, not a rebuild.
Flag anything that seems to need new backend surface rather than building a
placeholder for it — a parallel Codex scoping pass is happening for that.

Phase 1 scope (safe to build now — reorganizes existing data only):

1. NAVIGATION: Collapse sidebar to Overview, Decisions, Ledger, Settings.

2. OVERVIEW: One summary state, no duplicated lists. Three visually distinct
   tiers — Urgent (red), Waiting on you (amber), Insights (blue, view/acknowledge
   only). Tier mapping should follow real proposal_type values from brain-core,
   not the prototype's assumed names — confirm exact types with Codex before
   finalizing (flag_transaction/vendor_risk → Urgent is a guess, not confirmed).

3. DECISIONS: Merge current Inbox tabs and Audit Log's approval/rejection views
   into one filterable list (priority/status/type/search, as in the prototype).
   This is the single source of truth — Home and Vendors link into filtered
   views of it, not separate copies.

   3a. DETAIL MODAL: Tapping "View full detail" on any Urgent or Action-needed
       row opens the modal shown in the prototype — recommended action, why-this-
       needs-your-call, evidence table, linked evidence, confidence bar, what-
       happens-next, consequence box, flagged-by line, collapsible technical
       detail, Previous/Next navigation, Approve/Decline. Button labels change
       per proposal type (e.g. fraud shows Investigate/Dismiss, not Approve/
       Decline) — this needs real per-type action semantics from brain-core,
       see Codex scoping doc. Build the modal shell and wire it to whatever
       fields the API actually returns today; leave fields blank/hidden rather
       than fabricating data for anything not yet exposed (confidence score,
       matched rule name, linked evidence records).
   3b. BULK APPROVE: Checkboxes appear only on same-type items below the
       existing auto-approve threshold (see prototype's Riverside Co / Fenwick
       Traders example). A bulk-approve bar appears when 2+ same-type items are
       checked; disabled if mixed types are somehow selected. This should call
       existing single-item approve logic once per item, not a new bulk endpoint,
       unless one already exists.
   3c. Informational-tier items keep the lightweight inline expand from the
       prototype's v4/v5 pattern — no modal.

4. LEDGER: Collapse Bills/Income/Expenses/Liabilities into one Cash Flow tab.
   Keep Accounts, Vendors, Rules as tabs. Vendors drops its own approval
   workflow (moved to Decisions), becomes a pure directory.

5. GLOBAL SEARCH: One search bar above all three main pages, searching across
   Decisions, Vendors, and Accounts using existing data — not a new index/service.

6. SOURCES: Replace the current 4-step modal wizard with the prototype's single
   persistent Settings → Sources page + inline add-source form. Preserve the
   existing account-connection flow (whatever underlying OAuth/Plaid-style
   handoff already exists) — only the wizard-vs-page presentation changes.
   Extracted document items route individually into Decisions, never as a
   single bulk-confirm screen.

7. SETTINGS: Reorganize into Profile, Notifications, Team, Billing, Sources,
   Developers, plus existing Security/Legal/Account pages unchanged.
   - TEAM: Rebuild from the current Team page's real member data. Add
     per-member limit and backup-approver fields to the UI, but do not imply
     they're enforced unless Codex confirms brain-core checks them.
   - BILLING: Keep current stub behavior (plan selection / add card) until
     Codex confirms real usage-based billing data is available — do not
     fabricate the subscription-floor/success-fee numbers shown in the prototype.
   - DEVELOPERS: Nest Overview/API Keys/Tenants/Usage & Limits as sub-tabs
     here (not top-level nav). Keep API Keys' current honest "not enabled yet"
     empty state — do not make key creation appear functional if
     BRAIN_API_KEY_AUTH_ENABLED is still gated. Usage & Limits: scope the
     "requests by method" list to actual API calls only — exclude internal
     pipeline events (ledger.upload.projected, canonical.projected, etc.) from
     this business-facing view.

8. FIRST-RUN ONBOARDING: The 3-step walkthrough (a rule → what it auto-approves
   → what always needs approval) should trigger appropriately for new tenants
   without interfering with the existing demo-tenant flow — coordinate with
   whatever "first visit" detection already exists rather than adding a new one.

9. AUDIT LOG: Default view shows decision-type events only; system/pipeline
   events move behind a "Show system activity" toggle, off by default for
   non-admin roles.

Flag anything in the prototype that assumes a data shape you don't see in the
current API surface — don't invent fields or fake success states.
