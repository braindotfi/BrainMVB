Fix: anchor coverage is computed against only the most recent anchor window

In the Audit Log list, older events show "Pending" while newer events show "Recorded" — coverage appears to regress over time, which is impossible. Once an event is covered by an anchor window, that never becomes untrue.

Cause: anchorFor() in client/src/lib/brainAudit.ts derives coverage from /v1/audit/anchor/latest, which returns only the single most recent audit_anchors row for the tenant. Any event falling outside that one window's period_start/period_end is classified pending_next_batch regardless of whether an earlier anchor already covered it. This is invisible on a fresh demo tenant with one window; it mislabels all history as soon as there are two.

The per-event endpoint resolves this correctly — GET /v1/audit/event/{id} returns inclusion_proof.anchor_tx_hash and anchor_block computed against the anchor window that actually contains the event.

Please:

Change AuditRecordPopup.tsx to derive anchor state from the per-event endpoint's inclusion_proof rather than from the latest-anchor-derived value, so the detail view is always correct. Keep the same three-state logic and the same anchor_tx_hash !== null gate.
For the list view, the per-event endpoint isn't practical at 90+ rows. Note this limitation in a comment on anchorFor() and open a tracking issue for a batched coverage endpoint — brain-core would need something like a list of all anchor windows for the tenant, or a bulk coverage lookup. Don't work around it with N requests.
Add a test covering the multi-window case: an event whose timestamp precedes period_start of the latest anchor but which is covered by an earlier one should render as anchored, not pending.

Separately: the Audit Log page subtitle reads "Every decision is recorded, anchored, and verifiable" while no records are currently anchored. Soften it to something accurate regardless of anchor state — e.g. "Every decision is recorded, verifiable, and anchored on-chain."
